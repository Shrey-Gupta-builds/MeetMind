QUESTION 1: END-TO-END RAG LIFECYCLE
Q: "Walk me through the exact lifecycle of a user query in your RAG engine."

Interviewer is testing: Complete end-to-end understanding of RAG flow.

IDEAL ANSWER:
"1. Input: The user asks: 'What budget was approved for Q3?'
2. Query Embedding: The query string is embedded into a 384-dimensional dense
   vector using `all-MiniLM-L6-v2`.
3. Similarity Search: ChromaDB performs approximate nearest neighbor (ANN)
   search and returns the top 4 most relevant 500-character transcript chunks
   (`k=4`).
4. Context Formatting: `RunnableLambda(format_docs)` concatenates the 4 text
   chunks into a clean context block.
5. Prompt Augmentation: The context and user query are injected into the system
   prompt template.
6. Generation: Mistral AI generates the final answer grounded strictly on the
   retrieved context.
7. Output Parsing: `StrOutputParser` extracts the response string and sends it
   to the user."


--------------------------------------------------------------------------------
QUESTION 2: ANTI-HALLUCINATION STRATEGIES
Q: "How do you guarantee that your RAG assistant doesn't hallucinate facts not
   in the meeting?"

Interviewer is testing: RAG reliability, guardrails, and real-world deployment
   challenges.

IDEAL ANSWER:
"We enforce a three-layer defense:
1. Strict Negative Prompt Constraint: The system prompt explicitly commands:
   'Answer the user question based ONLY on the meeting transcript context
   provided below. If the answer is not found in the context, say: I could not
   find this information in the meeting transcript.'
2. Low Temperature (0.3): Restricts the model from sampling probabilistic,
   creative tokens, enforcing near-deterministic output.
3. Concise Context Window: Restricting retrieval to `k=4` focused chunks
   prevents confusing the model with contradictory or noisy background text."


--------------------------------------------------------------------------------
QUESTION 3: HYPERPARAMETER TUNING - TOP-K VALUE
Q: "Why did you choose `k=4` for retrieval? What happens if `k=1` or `k=20`?"

Interviewer is testing: Retrieval trade-offs (Precision vs Recall).

IDEAL ANSWER:
"It is a balance between **Recall** and **Precision (Signal-to-Noise Ratio)**:
- If `k=1` (Too small): Risk of false negatives. If an answer spans multiple
  paragraphs or was split across chunk boundaries, `k=1` misses essential
  context.
- If `k=20` (Too large): Context dilution. Irrelevant chunks clutter the
  prompt, increasing token costs, slowing down LLM inference, and increasing
  the risk of the model latching onto irrelevant details.
- `k=4` (Sweet spot): With 500-character chunks, 4 chunks provide ~2,000
  characters (~400-500 words). This fits comfortably in the prompt while
  providing sufficient context depth."

QUESTION 4: ADVANCED RAG IMPROVEMENTS
Q: "If a user query fails or retrieves the wrong chunk, how would you improve
   this RAG system?"

Interviewer is testing: Knowledge of Advanced RAG architectures.

IDEAL ANSWER:
"I would implement three proven Advanced RAG enhancements:
1. Re-Ranking (Cross-Encoder): Use a bi-encoder to retrieve top 15 chunks
   quickly, then apply a Cross-Encoder (e.g. `bge-reranker`) to score
   query-document pairs together and pass only the top 3 highest-scoring
   chunks to the LLM.
2. Hypothetical Document Embeddings (HyDE): Ask the LLM to generate a
   hypothetical answer first, embed that answer, and use it to search the
   vector database (bridges vocabulary gaps between questions and statements).
3. Hybrid Search: Combine dense semantic search (ChromaDB vectors) with sparse
   keyword search (BM25) using Reciprocal Rank Fusion (RRF) to capture exact
   acronyms, names, and numbers that vector embeddings sometimes blur."


--------------------------------------------------------------------------------
QUESTION 5: EVALUATION FRAMEWORK
Q: "How would you quantitatively evaluate the performance of your RAG pipeline?"

Interviewer is testing: RAG evaluation metrics (RAG Triad).

IDEAL ANSWER:
"I would use the **RAG Triad** framework (using tools like **Ragas** or
**TruLens**):
1. Context Relevance: Are the retrieved chunks actually relevant to the user's
   question? (Evaluates the retriever)
2. Groundedness / Faithfulness: Is the generated answer 100% derived from the
   retrieved context, or does it add outside knowledge? (Evaluates hallucination)
3. Answer Relevance: Does the final answer directly address the user's question
   without rambling? (Evaluates generator alignment)"
