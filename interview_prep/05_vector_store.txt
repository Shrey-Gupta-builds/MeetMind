QUESTION 1: EMBEDDINGS & MODEL SELECTION
Q: "Why did you choose `all-MiniLM-L6-v2` as your embedding model?"

Interviewer is testing: Understanding of vector embeddings, dimensionality, and
   performance trade-offs.

IDEAL ANSWER:
"1. Proven Industry Benchmark: `all-MiniLM-L6-v2` is a 6-layer BERT-based
   sentence-transformer model fine-tuned on over 1 billion sentence pairs for
   semantic similarity.
2. Low Dimensionality (384 Dimensions): Many OpenAI embedding models output
   1536 dimensions. 384 dimensions produce compact vector representations,
   requiring 75% less RAM and disk storage.
3. CPU Efficiency: It generates embeddings in under 15ms per chunk entirely on
   a standard CPU, eliminating the need for expensive GPU infrastructure during
   vector ingestion.
4. Open Source & Zero Cost: Completely free with zero external API latency or
   rate limits."

QUESTION 2: VECTOR SIMILARITY METRICS
Q: "How does Chroma calculate similarity between the query vector and document
   chunks?"

Interviewer is testing: Mathematical fundamentals of vector search.

IDEAL ANSWER:
"Chroma defaults to **Cosine Similarity** (or Squared L2 distance).
1. Vector Dot Product / Cosine Similarity: Measures the cosine of the angle
   between two multi-dimensional vectors:
   cos(θ) = (A · B) / (||A|| ||B||)
   - Value ranges from -1 to +1 (or 0 to 1 for normalized vectors).
   - Because `all-MiniLM-L6-v2` vectors are normalized to unit length (norm = 1),
     cosine similarity is mathematically equivalent to the inner dot product,
     making calculations exceptionally fast.
2. Why Cosine over Euclidean (L2): Cosine similarity measures directional
   alignment (semantic meaning) rather than vector magnitude (length of the
   text)."

QUESTION 3: DATABASE SELECTION (CHROMADB VS PINECONE VS FAISS)
Q: "Why did you choose ChromaDB over FAISS or a cloud vector database like
   Pinecone?"

Interviewer is testing: Database architecture, self-hosted vs managed services.

IDEAL ANSWER:
"It depends on system requirements and deployment target:
- ChromaDB: An embedded, serverless, local vector database (like SQLite for
  vectors). It requires zero server setup, persists directly to disk in
  `./vector_db`, supports metadata filtering, and is ideal for
  single-node/local applications.
- FAISS (Facebook AI Similarity Search): An extremely fast in-memory indexing
  library, but it lacks built-in metadata management and persistence
  abstractions out-of-the-box.
- Pinecone / Weaviate / Qdrant: Managed cloud vector databases. Necessary when
  scaling to millions of documents across distributed clusters with
  multi-tenancy, but adds external network latency, recurring cloud
  subscription costs, and vendor lock-in for a meeting assistant."

QUESTION 4: VECTOR COLLISION & SESSION ISOLATION
Q: "If a user processes Meeting A and then processes Meeting B, what happens in
   your vector store?"

Interviewer is testing: State isolation, multi-tenancy, and data leakage.

IDEAL ANSWER:
"If using a fixed collection name and static persistence directory without
cleanup, Meeting B's chunks are appended into the same collection as Meeting A.
When the user asks a question about Meeting B, the retriever could pull
irrelevant chunks from Meeting A.
How we solved it:
- In `build_vector_store`, we ensure the storage directory is cleared before
  indexing a new meeting.
- In an enterprise multi-user system, the production solution is **Namespace
  Partitioning**: dynamically assigning each meeting a unique
  `collection_name = f'meeting_{meeting_id}'` or indexing all chunks with
  metadata `{'meeting_id': meeting_id}` and applying metadata filters during
  retrieval."
